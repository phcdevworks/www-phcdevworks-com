# PHCDevworks Website Roadmap

`www-phcdevworks-com` is the flagship public website for PHCDevworks. It
presents the company, its ecosystem, and its technical initiatives. Spectre is
the primary platform under that umbrella, not the whole identity of the site.

The site runs as an SSR application on Cloudflare Workers via
`@astrojs/cloudflare`, built with Astro and Spectre UI Astro.

---

## 1. Foundation Status -- In Progress

Core site structure is in place. Routes, layout, navigation, header, footer,
homepage, and initial product pages are built and passing `npm run check`.

Current Spectre dependency versions: `@phcdevworks/spectre-tokens ^4.0.0`,
`@phcdevworks/spectre-ui ^3.1.0`, `@phcdevworks/spectre-ui-astro ^4.2.0` --
bumped 2026-08-02 to close the version lag behind `project-design`'s latest
releases (this followed an earlier Astro major bump, `^6.4.8` to `^7.1.3`).

### What is in place

- `Layout.astro` with site header, nav, and footer.
- Homepage with hero, product card grid, and principles section.
- Route pages for Spectre Design, Spectre Shell, and Spectre WordPress.
- Global CSS baseline layered on Spectre tokens.
- Cloudflare Workers SSR configuration via `@astrojs/cloudflare`.
- Full validation gate: `npm run check` (build + typecheck).
- Multi-agent team (Claude Code, Codex, Copilot, Jules) with documented
  authority boundaries in `AGENTS.md`.

### What will not change

- Company-first framing. This is the PHCDevworks website, not a Spectre-only
  site.
- Spectre packages and patterns before custom alternatives.
- Dark, technical, typography-first visual direction per `BRAND.md`.
- SSR-first, Cloudflare Workers-compatible implementation.
- No button-led CTA defaults on impact sections.

## 3. Roadmap -- Active Phase

P0 is complete. The active phase adds reusable components and sharpens
presentation and production quality across all routes.

---

### P1: Reusable Component Foundation

**Objective** Extract repeated layout patterns from pages into `src/components/`
once a pattern is stable enough to reuse without forcing premature abstraction.

**Why it matters** The current layout patterns are embedded directly in pages.
When a pattern repeats across three or more pages in the same form, extracting
it reduces drift and makes page work easier to maintain.

**Deliverables**

- Add `src/components/` when the first genuinely reusable component is
  identified.
- Keep extraction focused -- do not prematurely abstract one-off patterns.
- Document component props and usage inline with the Spectre UI Astro approach.

---

### P2: Accessibility, Metadata, and SEO

**Objective** Raise the baseline quality of accessibility, page metadata, and
search presentation across all routes.

**Why it matters** The core layout and pages are functional but have not been
audited for keyboard navigation, screen reader labels, OG metadata, structured
data, or robots configuration.

**Deliverables**

- Audit all pages for keyboard navigation and screen reader label completeness.
- Add Open Graph and Twitter card meta tags to `Layout.astro`.
- Add `robots.txt` and `sitemap.xml` if not already generated by Astro.
- Verify `<title>` and `<meta name="description">` are accurate and useful on
  every route.
- Document accessibility findings in `CHANGELOG.md [Unreleased]`.

---

### P3: Responsive Polish and Performance

**Objective** Verify all pages are solid on mobile and narrow viewports, and
check for obvious performance regressions on the Cloudflare Workers runtime.

**Why it matters** The site is tested primarily at desktop breakpoints during
development. Mobile presentation needs a deliberate check pass before the site
is treated as production-ready.

**Deliverables**

- Review all pages at mobile, tablet, and wide-desktop viewports.
- Fix any layout breaks, overflow issues, or unreadable type at narrow widths.
- Check that Cloudflare Workers cold-start latency is acceptable for SSR routes.
- Add font subsetting or loading optimizations if Space Grotesk load time is
  measurable.

---

## 4. Explicitly Out of Scope

- Upstream token definitions -- owned by `@phcdevworks/spectre-tokens`.
- A parallel design system disconnected from Spectre.
- Generic marketing filler, decorative stock imagery, or SaaS-template layouts.
- Blog, CMS integration, or content management -- not planned unless explicitly
  requested.
- Moving this repository toward a single-product Spectre identity.

---

## 5. Recommended Execution Order

1. **P1 -- Component extraction** -- implement only as patterns stabilize; do
   not force abstraction ahead of repeated use.
2. **P2 -- Accessibility, metadata, SEO** -- lower risk if deferred briefly but
   should be resolved before treating the site as fully production-ready.
3. **P3 -- Responsive polish and performance** -- validate once P2 is stable
   so the full page content is in place before a layout audit.
